# CLAUDE.md

tea-pos v2: the rebuild of tea-pos. Vite and React apps on Cloudflare Pages, Go on Railway, Supabase for the database, login and files. Built for slow Android phones: every choice favours light and fast.

## Quick start

```bash
corepack enable        # once: pnpm comes from package.json's packageManager
pnpm install
pnpm lint
pnpm typecheck
pnpm format            # Prettier, 4 spaces
supabase migration new <name>   # migrations live only here; never name one by hand
```

Go, against the staging database: `cd api && infisical run --env=staging --path=/app -- go run ./cmd/api` (needs `infisical login` once).

`pnpm backoffice`: local Go and local Vite together, on the staging database (`scripts/dev.sh`; restart it after a Go change). The API's reference: `http://localhost:5173/api/docs`, on a laptop only. `pnpm backoffice:prod`: the same on production's database; Vite refuses every write but sign-in (`READ_ONLY`), so test saves on staging. `pnpm seller`: Vite against the staging API (`API_ORIGIN=http://localhost:8080 pnpm seller` uses a local Go instead). Vite proxies `/api` to staging the way the Pages forwarder does, adding `EDGE_SECRET`. `pnpm bundle-size` (after `pnpm build`) checks each app's first screen against its budget in `scripts/bundle-size.mjs`; until v1 retires both budgets are 500 KB, so no step stops to trim; they come back down after the migration. `pnpm bench <url>` runs the RFC's benchmark (20× CPU, Slow 4G, signed in, medians of 3 reopens and 3 first visits); `pnpm bench --sign-in <url>` once per app first.

Database:

```bash
pnpm --filter @tea-pos/api db:schema         # dump staging's structure to api/db/schema.sql; rerun after every migration
pnpm --filter @tea-pos/api generate          # sqlc (db/queries -> internal/store) and the contract (internal/contract -> openapi.yaml)
pnpm --filter @tea-pos/api-client generate   # openapi.yaml -> packages/api-client/schema.d.ts
TEST_DATABASE_URL=postgres://postgres:postgres@localhost:5432/postgres?sslmode=disable \
  pnpm --filter @tea-pos/api test:integration   # needs a local Postgres 17 (OrbStack)
```

**Migrations reach the databases only through CI:** a PR into `staging` comments what would run (`migrations.yml`); `deploy.yml` runs them before the API, on the merge into staging and on a release after the owner approves; never `supabase db push` by hand. Never edit a migration that has run (fix it with a new one), and write backfills so running twice is harmless. **Migrations change the databases; `api/db/schema.sql` describes them.** Its first line marks the newest migration staging had when dumped; `api/db/pending.sql` (generated by `generate`) holds every newer one, so sqlc and the tests see a PR's migration before it reaches staging. The migrations cannot build a database from scratch (the base tables predate them), so tests load the dump plus `api/db/stubs.sql` (Supabase's `auth` and roles). Integration tests: `api/tests/integration/`, build tag `integration`, one throwaway database per test via `testkit.DB(t)`. **End-to-end tests:** `api/tests/e2e/`, build tag `e2e`, against the deployed `staging` through each app's `/api` (`pnpm --filter @tea-pos/api test:e2e`, with `TEST_LOGIN_KEY`); `deploy.yml` runs them after every staging deploy (commit status `e2e on staging`); the release PR's `e2e` check (`e2e.yml`) reads that result, and runs them itself only when there is none or by hand; after `seed.sql` (the fake users of the `test-` tenants). They sign in with **the test sign-in, `POST /auth/test`: compiled in only with `-tags testlogin` (staging's build), refused in production by config, and only for users of `test-` tenants alone.** `pnpm lint` and `pnpm typecheck` cover Go too (`gofmt`, `go vet`, `go build`). Dependencies are added only when they remove real work; today `klauspost/compress` (gzip), `jackc/pgx` (Postgres) and `danielgtaylor/huma` (the contract).

**The contract:** request and response shapes are Go structs in `api/internal/contract/`, registered in `internal/handler/` through `route(api, op, access, fn)`, never `huma.Register` directly. **Every route declares who may call it** (`auth.Public`, `auth.SignedIn`, `.InTenant()` for `/tenants/{tenant}/...`, `auth.App("backoffice", auth.Guest)` for reads and `auth.Admin` for writes, `.RateLimit()`); a route without one is refused at runtime and fails the permission test (`tests/integration/permission_test.go`). Handlers read the caller with `auth.CallerFrom(ctx)`. **Access is per app** (`user_app_access`: a level per tenant, user and app; each app offers only some, `auth.Levels`); the owner is always an admin, an inactive member is out, and anyone without a level row falls back to `users.role` until v1 retires. Screens hide writes with `useAccess()`. `api/openapi.yaml` and `packages/api-client/schema.d.ts` are generated from them, never edited; CI fails if either is out of date. Every error is `{"status", "code", "message"}` from `internal/httpx`: `code` is stable and the apps translate it.

Node 22 (`.nvmrc`), TypeScript 5 (not 7: `openapi-typescript` needs 5's JavaScript API).

## Layout

```

  cmd/api            REST API and webhooks
  cmd/realtime       WebSocket hub
  cmd/worker         background jobs and schedules
  internal/config    environment, read once, bad values refuse to start
  internal/platform  logging and the HTTP server (graceful shutdown)
  internal/middleware request id, log, recover, gzip, timeout
  internal/contract  request and response shapes (Huma); openapi.yaml is generated from them
  internal/httpx     the one error shape: {status, code, message}
  internal/auth      Google sign-in through Supabase, sessions (sessions table, cookie), the access middleware
  internal/telemetry PostHog, only from Go: errors, the apps' events (/events), flags evaluated in memory
  internal/domain    pure business rules, no database or HTTP; the only unit tests live beside them
  internal/jobs      River (the queue in Postgres, schema river): job kinds, v2's cron, Insert inside the change's transaction
  internal/weather   Tomorrow.io per weather cell (stores grouped by area), for the worker

  internal/files     signed Storage addresses: phones upload photos straight to Supabase
  internal/idem      writes saved once per Idempotency-Key, in the write's own transaction
  internal/page      cursor paging (time, id) and since, for every list

  internal/store     GENERATED by sqlc from db/queries

apps/seller, backoffice  Vite apps, Pages projects tea-pos and tea-office. app.config.ts: everything that differs
                     per app (name, brand colour, sign-in words, languages). src/routes: TanStack Router file
                     routes (routeTree.gen.ts generated). functions/api forwards /api to Railway
packages/config/     the shared Vite setup (React Compiler, Tailwind, PWA, routes) and tsconfig for apps

                     layout/ (Panel, ListRow, Sheet, Drawer), feedback/ (EmptyState, Skeleton), controls/ (SearchBox, Badge,
                     Avatar), form/, chart/, photo/, lib/ (ICON, motion); styles/motion.css the shared animations
```

## Where things live

- **The plan:** the Notion RFC [Next architecture for the tea-pos app suite](https://app.notion.com/p/3f495a715405812eae99d02d37240af8). It holds every decision with its reason and the build order (Step 1 onward). Read the relevant section before starting a step.
- **The how, per step:** `.claude/tasks/NNN_name.md`, NNN = the step number. Use the `task-file` skill.
- The old app is `../tea-pos` (reference for features and business rules only; its architecture rules are replaced by the RFC).

## How we work

- **One step at a time, in build order.** Later steps assume earlier ones exist.
- **Features are vertical slices:** the Go endpoint and its screen together, one PR.
- **No Next.js.** Code copied from the old repo drops its Next.js imports on the way in.
- **One component library for every app** (`packages/ui`, `packages/shell`). Copy a component from the old repo when a screen first needs it, not before. Where the old apps do the same job two ways, keep one and tell the owner. Every dependency earns its place; heavy ones load lazily.
- **Route data for the shell lives on the route:** `staticData: { shell: { titleKey, parent, ... } }` (`packages/shell/frame/routes.ts`).
- **Task file first.** Write it, the owner reviews it, then code. Every change, not only big ones.
- **Every change is a PR into `staging`** (not the default: `main` is, so set the base; a PR into `main` from anywhere but `staging` fails `release-source`), squash merged; use the `pr` skill. `staging` deploys to Railway's `staging` environment on the staging database.
- **A release is a PR `staging` → `main`,** merged with a **merge commit**, never squash; use the `release` skill. It tags a GitHub Release `YYYY.MM.N`. Neither branch takes a direct push (rulesets in `.github/rulesets/`, applied with `gh api`).
- **Security:** Dependabot opens one grouped PR a week per ecosystem into `staging`; review and squash-merge it like any other (it gets no Pages preview or PR comments: no secrets). `govulncheck` in `checks` fails on a vulnerability our Go code calls: bump the module, or Go itself (`api/go.mod` and the Dockerfile together). `dependency-review` blocks a PR adding a high-severity package. CodeQL runs from GitHub's default setup.
- **CI tests each change once, at its PR** (`ci` runs on PRs only; `staging` requires a PR to be up to date, so its checks ran on exactly what merges). **A merge deploys, in order** (`deploy.yml`): Railway config → migrations (production: the owner's Approve) → the API at that exact commit (`scripts/railway-deploy.mjs`) → the apps → staging: e2e / production: a read-only check. **Railway never deploys by itself** (`railway.ts`: a trigger on the unused branch `railway-manual`, Wait for CI off), so no workflow waits on another. The release PR reads staging's e2e result and runs the benchmark (`pnpm bench`, 3 runs, information only). **Everything about a change shows on its PR:** checks before the merge, then a live deploy comment. Task 015b.
- **Each CI result gets its own PR comment, in one template,** edited in place (`.github/actions/report`: a status header with commit, time and run link, a row per step, then details; on failure the last log lines).
- **Ask before pushing or opening a PR.** Local commits are fine.
- **Railway as code** (`.railway/railway.ts`): never change a declared setting in the dashboard (the next apply fails). A release PR that changes it shows production's plan as a comment; the release's deploy applies it first. Never name a real branch in a service's source, and never leave it out (that means `main`): Railway would deploy by itself again. **Every variable must be declared in the file**; one Infisical syncs in is declared as `preserve()`, or the next apply removes it.
- **Foundations every app uses** (Steps 17-17e): **background work and schedules are River jobs in the worker** (`internal/jobs`; every schedule a line in `jobs.Schedules` with its production and staging timing, run on Railway only, `JOBS_SCHEDULE`), queued with `jobs.Insert` inside the change's transaction, never outside one; webhooks only for outside services. **Live updates:** after a change, `realtime.Announce` on the same transaction; the hub tells every socket watching that topic (`user:`, `tenant:`, `store:`), the app refetches the queries whose `meta.live` names the kind (`packages/api-client/live.ts`); writes always go through the API, the hub only delivers. **Photos:** `PhotoInput` shrinks on the phone (1080 px, WebP 0.6, at most 0.4 MB) and uploads straight to Supabase with an address from `POST /tenants/{tenant}/files`. **Every write route is `.Idempotent()` (saved once per `Idempotency-Key`, its change on `idem.Queries(ctx, q)`) or `.Repeatable()`**; the permission test fails otherwise; screens write through `useApiMutation`. **Every error is a package-level `httpx.New` var**: the contract lists every code and the apps' typecheck fails on one without `errors.<code>` in both languages. **Lists** page by `page.Input` / `page.Output` and `useInfiniteList`. **The app frame:** every screen under `/<tenant>/`; one store picker (`app.config.ts` `stores`: `one` for seller, `all` with All stores for backoffice), `useFlag`, shared Account, More and What's new (`packages/shell/whats-new.json`, written by the release skill). Tasks 017-017e.
- **Monitoring: the phones never load PostHog.** The apps queue errors and page views (`packages/shell/lib/events.ts`) and send them to `/api/events`; Go forwards them, and every error Go logs, to PostHog (`internal/telemetry`); flags are evaluated in Go and come back on `/me`. `ops-maintenance` answers 503 to everyone but admins. **A flag is checked in Go, not only in the screen** (a route behind a flag refuses while it is off); one flag per purpose, rules on `role`, `app`, `tenantId`, `storeId`. Each page load reports `app_ready` (the `tea-pos:ready` mark `pnpm bench` reads; the bench checks they agree); `pages.yml` uploads source maps to PostHog and deletes them. Every request carries `X-App-Version` (`seller@2026.10.3+a1b2c3d`), every response `Server-Timing`; `MIN_APP_VERSION` makes older apps update (426). A new build is noticed from `version.json` (static, never cached; `frame/AppUpdate.tsx`), so the update shows in a tab's header before the download. The version is the release PR's title, `staging` on staging (`deploy.yml`). Tasks 016b, 016c.
- **Every app reaches the API on its own address** (`/api`, a Pages Function from `packages/edge`): no CORS, and previews behave like production. Go answers 404 to anything without the right `X-Edge-Secret`, except `/health`. `pages.yml` deploys a PR's previews against the staging API; `deploy.yml` calls it for staging's alias and for production, after the API (`API_ORIGIN` in each app's `wrangler.toml`).
- **Settings outside git** (Cloudflare, Infisical, Supabase, dashboard-only Railway settings) are the owner's to click: write down what to click, never assume it was done.
- **Secrets live in Infisical** (`staging`, `prod`), never in git or the Vite build. The repo is public.

## Writing

- **Commits:** `type(scope): short summary`, as short as possible, no body. **No `Co-Authored-By` or `Claude-Session` lines**, in commits or PRs.
- **PR descriptions:** a few lines: what and why, and the task file.
- **Code comments:** rare, one short line, only where the why is not obvious.
- **Replies to the owner:** short and simple.

## Keep this file updated

Only for structural changes: a new package, layer, rule or command. Not for single endpoints or fixes.
